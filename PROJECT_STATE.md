  - THE INTEGRITY RISK THIS PIECE HAD TO SOLVE, and the fix. The assembly template takes an OPTIONAL chain context (the chosen gatekeeper's name, role, company, and win condition), and for a decision maker generated FROM a chosen gatekeeper that chain is what writes the "you already had a discovery meeting with X, and you earned this meeting" narrative into BOTH text fields. That chain was built at generation time and then THROWN AWAY: generation_fields stored only the candidate and the admin's inputs, and nothing on the row pointed back at its gatekeeper. So rebuilding such a candidate without it would have silently deleted that narrative and turned a second meeting back into a standalone one, on ANY edit, including editing the persona name or role that appear in the narrative. THE FIX: generation_fields is now VERSION 2 and stores the chain, so re-assembly is fully self-contained from the candidate row. Nothing looks the gatekeeper up again, so the two scenarios stay independently assignable with no prerequisite, exactly as before.
  - The version bump is UNCONDITIONAL, on every new generation including a gatekeeper that has no chain. Version 2 has to mean "provenance is fully recorded," because that is what lets an ABSENT chain on a version 2 decision maker be read as proof it never had one.
  - HOW THE CHAIN IS RESOLVED ON AN EDIT: from an explicit table keyed on the row, never a guess. A chain is only ever built in the "generate from a chosen gatekeeper" branch, and that branch forces the new persona to be a decision maker, so a chain always implies a decision maker and a GATEKEEPER NEVER HAS ONE. That gives: gatekeeper at any version, no chain; version 2 decision maker with a stored chain, that chain; version 2 decision maker with none, standalone; version 1 decision maker, GENUINELY AMBIGUOUS and REFUSED, with a message telling the instructor to regenerate the case and edit the new candidates. Legacy version 1 rows cannot be recovered because version 1 stored no chain either way and nothing points back at the gatekeeper. Regenerate-only was the owner's confirmed choice; a text-sniffing rescue was considered and deliberately NOT built, to keep the one route that must be beyond doubt simple.
  - THE ROUND-TRIP GUARD (the extra safety net). Before overwriting anything, the route re-assembles the UNEDITED stored fields with the resolved chain and requires them to reproduce the saved text EXACTLY. The saved text was itself produced by this same template at generation time, so a mismatch means the reconstruction is wrong (a missing or wrong chain, or a bug in how it is stored) and the edit is refused with nothing written. It is strict on version 2 rows and warns rather than refuses on version 1 gatekeepers, which predate chain storage. IT ASSUMES lib/persona-assembly.ts IS FROZEN: if that template is ever changed later, existing version 2 candidates will no longer reproduce their saved text and will need regenerating before they can be edited. That is the honest outcome, because after a template change a rebuild really would drift. The assumption is written as a comment on the guard itself. An attacker declares 1 KB and ships a deflate stream that inflates to gigabytes, because the inflater works from the stream and never consults the declaration. **SO THE ONLY LIMIT THAT BINDS A HOSTILE FILE IS THE 512 KB BYTE CAP, AND DEFLATE'S MAXIMUM RATIO IS ABOUT 1032:1, WHICH MEANS 512 KB OF HOSTILE INPUT CAN STILL REACH ROUGHLY 500 MB IN THE FUNCTION.** **THAT RESIDUAL IS ACCEPTED, NOT SOLVED, AND THE REASONING IS:** the real fix is a bounded inflate, ExcelJS does not expose one, and replacing the unzip layer is not justified by this threat model, because the route sits behind `requireInstructorRequest()`, instructors are added only by a super admin, and no anonymous caller can reach it. **IF THAT CHANGES, THIS DECISION CHANGES**: opening rubric upload to a wider group, or to any unauthenticated path, is the trigger to revisit it. The owner made this call on 2026-09-09 after identifying the lying-central-directory limitation, which the first version of the code comments had overstated as a zip-bomb defence. **BOUNDARY FIXTURES EXIST AND ARE TWO-SIDED**: `just-over-the-size-cap.xlsx` is exactly cap plus one byte and must refuse ON SIZE specifically, and `near-the-size-cap-valid.xlsx` is a real 502,352-byte rubric that must still PARSE, because "refuses things over the cap" is also satisfied by a guard that refuses everything. Both read the cap out of `lib/types.ts` so they cannot disagree with it. **A SMALL FINDING FROM THAT BOUNDARY TEST, KEPT AS AN EXAMPLE OF WHY ONE-BYTE FIXTURES BEAT COMFORTABLE ONES:** `formatBytes()` originally rounded to nearest, so a file one byte over the cap produced "That file is 512 KB and the limit is 512 KB".
