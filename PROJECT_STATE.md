  - Transcript: captured in the browser from the Realtime events (Alex's speech, and the student's speech transcribed by gpt-4o-transcribe), then saved turn by turn through the server using the service-role key (the server stays the only writer). Transcript accuracy confirmed high in testing.

The approach is persona-agnostic, so it will cover Jordan later with no change. Recording is capped at about 1 Mbps video plus 96 kbps audio (roughly 8 MB per minute of call) so files stay small and uploads stay reliable.
  - Encoder tuned to stay out of the live call's way. The recorder uses the lighter VP8 codec (not VP9) and captures at 720p/24fps. Early testing showed brief choppiness in Alex's live audio on a couple of responses; it was traced to the recording's encode load (a camera-off call was consistently clean), and these lighter settings fixed it (confirmed clean on the live URL). 720p is still clear enough for later delivery review.
  - Camera defaults on in practice, with an on/off toggle. Off records nothing and video_path stays null. The camera-required-and-locked rule for graded submissions is intentionally NOT here; it is Stage 7 and sits on top of this capture and storage (using the session's kind and mode) with no change needed here.
  - Upload mechanism (decision, tradeoff explained to the owner): a server-minted one-time signed upload URL. The browser uploads the file straight to Supabase Storage, which bypasses the app's request-size limit (about 4.5 MB on Vercel), the server picks the exact storage path, and the service-role key never leaves the server. Sending the file through the app was rejected for that size limit.
  - Storage: a private bucket named session-videos (not publicly readable). Files are stored at <student-user-id>/<session-id>.webm, so the first folder is the owning student's id. Access rule (supabase/stage-5-storage.sql): a student can download only the files in their own user-id folder; there is deliberately no student write rule (uploads use the server-minted signed link), mirroring sessions being server-written (decision A). The service-role key never reaches the browser.
  - Cross-student isolation verified in production: each student's recordings sit in their own user-id folder, and a second student who pasted another student's exact results URL got a 404 (the session RLS blocked the read, so no video link was ever minted). This extends the Stage 2 session-isolation check to the video.

  - Storage limits: the Supabase project upload limit and the session-videos bucket limit were raised to 200 MB (Pro plan) after the default 50 MB rejected a test clip. At about 8 MB per minute, real-length calls stay well under 200 MB.

  - A graded submission is ONE continuous, one-shot attempt with NO resume (owner decision, a deliberate change from an earlier resume idea).   - No-resume is enforced server-side without fragile machinery (no heartbeats, timers, or background jobs): a resume WINDOW (60 minutes from the session's created_at, a single constant SUBMISSION_LIVE_WINDOW_MS in lib/submission.ts) keeps an attempt live only while it is in_progress and inside the window; after the window the server treats it as locked. A short-lived browser marker is the front-line UX that distinguishes an accidental refresh (stays live) from leaving (locks). Because the window is server-enforced, tampering with the marker can at most let a student continue their OWN attempt within the window, never start a second one. The shared routes a submission passes through (chat, voice connect, voice transcript, video upload, scoring) all refuse a locked submission; all session writes stay server-side with the service-role key (decision A).
  - Reload behavior (owner decision): a TEXT reload resumes losslessly (the conversation reloads from the server and continues). A VOICE+VIDEO reload LOCKS, because a page reload physically ends the live call, the AI's short-term memory, and the in-progress webcam recording, so it must not silently continue with a gap; it lands in the same locked screen with the transcript-so-far preserved. A browser warning fires before a reload or tab close on any live graded attempt (the in-app Back button cannot carry that browser prompt, but using Back still lands safely in the locked state with no data lost).
